In the hands-on, you started every app yourself

Details · slide 3

What was counted

  • Every FGCZ sequencing order finished over one year, read from the job history of SUSHI.
  • Orders that received only quality control were set aside; the rest are the “real analyses”.
  • Of those, about 7 in 10 ran two or more apps one after the other.

What it does not show

  • That the chains were the same: they were not (slide 8).
  • How long a person waited between the steps.
  • Which choices were hard: the genome and the comparison groups are the two you made yourself.

The genome is looked up; the LLM may only suggest

Details · slide 7

The order of the checks

  • 1. The dataset’s Species column names one species on FGCZ’s curated list → its reference is used.
  • 2. Otherwise, the species on the order’s B-Fabric samples.
  • 3. Otherwise, the LLM is asked to pick one name from the list, or UNKNOWN.
  • Code then checks: the name is on the list, the reply came from the expected model on an FGCZ server.
  • A person must confirm the suggestion before the chain may start.

What it does not show

  • How often step 3 is needed: about half of FGCZ’s raw datasets name a curated species in step 1.
  • Whether the model’s suggestions are good: step 3 was added in October 2026 and is a prototype.
  • Datasets with two species: there is no single reference, so OMAKASE refuses.

Why a closed list? A free answer could be a genome build that does not exist. A name on a list can be checked by code.

Past orders do not agree on one right analysis

Details · slide 8

What “~1 in 5” means

  • For each kind of order (service type), take the chain of apps used most often in the past.
  • Ask: would proposing that chain have been right for each order? About one time in five, yes.
  • For standard sequencing orders it was right less than one time in ten: they used more than 100 different chains.
  • This simple rule is the bar any automatic choice has to beat.

What it does not show

  • That a trained model would do as badly: no model has been trained or tested on this yet.
  • That the data are bad: real analyses simply differ.
  • A test with fixed rules, written before any results, will decide later whether an automatic choice is good enough.

Counted from FGCZ’s job history over one year. Numbers rounded.

Run side by side; stop at the first failure

Details · slide 9

The run on slide 9

  • FastQC, FastQ Screen, STAR, then featureCounts, on 2 mouse samples, on FGCZ’s test system (September 2026).
  • Side by side: 6 min 31 s from start to finish.
  • The same jobs one after another would have taken 12 min 13 s.
  • The recipe says which step waits for which (appendix B1).

What it does not show

  • Real datasets: with more samples, STAR takes much longer and the saving changes.
  • Every failure stops the chain: a short cluster hiccup is retried once before the chain stops.
  • Undoing work: jobs already running when another step fails keep running.

A model trusts what it is shown, even a cut-off list

Details · slide 11

What happened

  • A tool returned a long list. To fit the context window, the program cut it in the middle — without saying so.
  • The model answered confidently that there were no notes about OMAKASE. There were nine.
  • The fix: the program now writes “output cut here” into the text the model reads. The same question then listed all nine in one call.

What you can take from it

  • When you paste data into a chat, check that it all arrived.
  • Ask the model to say when it may be missing something.
  • Count important things yourself: “none” is the answer most likely to be wrong when input was lost.

Found by testing on FGCZ’s test system, September 2026; not by reasoning.

LLM, token, context window, prompt

Appendix A1

LLM — large language model

A program trained on a very large amount of text. Given text, it predicts what comes next, piece by piece. That is how it answers, summarises and writes code. It does not run anything: when an LLM “does” something, another program did it for it (A2).

Token

The pieces an LLM reads and writes. In English one token is about 4 characters, or three quarters of a word: 1,000 tokens ≈ 750 words. Price, speed and limits are counted in tokens.

Context window

Everything the model can see in one turn: the instructions, the conversation so far, the descriptions of the tools it may use, and the results of tools it called. The model on slide 10 has 262,144 tokens — roughly a few hundred book pages. What does not fit is cut, and the model does not know what it lost (slide 11).

Prompt

The text sent to the model. A good prompt says what is wanted, gives the data, and says what to do when the answer is unknown (“say UNKNOWN”, as on slide 7).

vLLM, and where the model runs

Appendix A5

vLLM

  • Open-source software that runs (“serves”) an open-weight LLM on GPUs you own.
  • Answers many requests efficiently by batching them on the GPU.
  • Speaks the same API as OpenAI’s hosted models (/v1/chat/completions), so the same client code can talk to a hosted or an on-premises model.
  • Supports tool calling: the model can reply with a tool call (A2).
  • The model it serves can change; programs ask the server which one it has (/v1/models) instead of assuming.

On-premises vs. hosted

  • Hosted: the model runs at a provider; your text travels there.
  • On-premises: the model runs on FGCZ’s own server; order data stays inside FGCZ. OMAKASE’s chat and its genome suggestion use only this.
  • One shared GPU server: the panel sends one request at a time, so many users at once means waiting, not a bug.
  • Open-weight model: its trained parameters can be downloaded and run locally, unlike most hosted models.

API and tokens: how a program uses Omics-Studio

Appendix A6

How a program signs in (no password)

  • The program shows a short code. You open B-Fabric, which already has the code filled in, and approve.
  • The program receives a token: a long random string that works for a limited time and can be renewed.
  • Tick “allow job submission” to give the token the right to submit. That right is a scope; without it, the API answers 403 insufficient_scope.
  • An AI agent such as Claude Code can use the token, so it can read datasets and submit jobs without ever holding a password.

What a request looks like

curl -H "Authorization: Bearer $TOKEN" \
     <OMICS_STUDIO_API>/api/v1/projects

curl -X POST -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"job": {"dataset_id": 12345,
          "app_name": "Fastqc",
          "parameters": {"cores": 1}}}' \
     <OMICS_STUDIO_API>/api/v1/jobs

The first lists your projects; the second submits FastQC on a dataset. The address is given in the exercise.

What a recipe file looks like

Appendix B1

A recipe, shortened

id: rnaseq_meeting_shape
version: 2
steps:
  - id: fastqc
    app: FastqcApp
    after: []            # starts with the chain
  - id: fastqscreen
    app: FastqScreenApp
    after: []
  - id: star
    app: STARApp
    after: []
    params:
      refBuild: "{{ reference_for(species) }}"   # looked up (slide 7)
  - id: featurecounts
    app: FeatureCountsApp
    after: [star]        # waits for STAR only
match:
  service_type: []        # empty: never chosen automatically

How to read it

  • A recipe is a text file (YAML). A bioinformatician writes it and signs it off; an AI may only draft one.
  • after says which step waits for which. Empty means “start with the chain”.
  • The genome is not written in: it is filled in from the dataset’s Species before a person approves.
  • There is no differential-expression step: choosing the comparison groups is a judgement nothing here can make.
  • A recipe has a version. A proposal records which version it used, so a result can be traced back.
