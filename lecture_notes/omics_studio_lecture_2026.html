NGS data analysis needs a cluster and pipeline code

Details · slide 3

What a cluster is

  • Too big for a laptop: one RNA-seq sample gives a BAM file of often more than 2 GB; many samples need many CPU hours.
  • Many computers that share one storage. At FGCZ the results land in gStore.
  • A scheduler (SLURM at FGCZ) keeps a queue. Each job asks for CPUs, memory and scratch disk, and waits until they are free.
  • Reproducible: someone else, later, gets the same result from the same data. That needs the data, the steps, the parameters and the software versions.

What it does not show

  • Small data can run on a laptop; the cluster is for size and for many samples at once.
  • Cloud computing works the same way: a queue in front of rented computers.
  • The 2 GB: it depends on the number of reads (details of slide 6).

Scripts are exact; web tools are easier to start

Details · slide 4

A whole job script (bwa.sh)

#!/bin/bash
# work in a scratch folder on the compute node
cd /scratch && mkdir -p test && cd test
cp LOCATION_OF_REF/reference.fasta .
bwa index reference.fasta                  # prepare the reference
cp LOCATION_OF_DATA/data.fastq.gz .
bwa mem -t 8 reference.fasta data.fastq.gz > aln.sam   # map, 8 CPUs
samtools view -bT reference.fasta -o aln.bam aln.sam  # SAM to BAM
samtools sort -o aln.sorted.bam aln.bam
samtools index aln.sorted.bam              # makes .bai
cp aln.sorted.bam* LOCATION_OF_STORAGE     # keep the result

# submit it:  sbatch -p user -n 8 --mem=100G bwa.sh

How to read it

  • Copy in, compute on the node’s own disk, copy the result back to storage.
  • sbatch hands the script to the scheduler with the CPUs and memory it needs.
  • Web tools (Omics-Studio, Galaxy, the commercial CLC Genomics Workbench) are easy to start but offer only their own tools.
  • Omics-Studio builds such a script from the App and your parameters with plain code, and keeps it next to the result (Part 2). It is deterministic: the same choices always give the same script. No AI writes it.

What it does not show

  • BWA is a DNA mapper. For RNA-seq you use a spliced mapper such as STAR (details of slide 5).
  • Tool versions: the script must also say which version of each tool to load.

RNA-seq: place each read on the genome, then count

Details · slide 5 (1 of 2)

What a read and a count are

  • A short read is a short piece of sequence read from the RNA in a sample, often 50–150 letters.
  • Which gene a read came from is unknown until it is placed on the genome: that is mapping.
  • Then the reads on each gene are counted. More reads on a gene means more of that gene’s RNA in the sample, roughly.
  • Comparing the counts of the same gene between groups shows which genes change. The differential expression (DE) test also corrects for how many reads each sample got in total.

What it does not show

  • The drawing has 12 reads; a real sample has millions.
  • Reads that span an intron: next page.
  • Reads that fit several places, or no gene: the tools have rules for them (details of slide 7).

Reading the examples on slide 6

  • FASTQ: 4 lines per read — name, sequence, +, a quality letter per base.

  • Sizes depend on the number of reads. As BAM, an exome is often 2–10 GB, a whole genome 100–300 GB.
  • The example rows on slide 6 are made up.

Omics-Studio writes the script and keeps it with the result

Details · slide 8

One result folder

  S1_undiff.bam             the results
  S1_undiff.bam.bai         (and the other samples)
  scripts/                  the job scripts that ran

  input_dataset.tsv         the DataSet it started from
  dataset.tsv               the new DataSet

Omics-Studio runs the same Apps as SUSHI, its predecessor at FGCZ; the folder layout comes from the Apps’ code (sushi_fabric), read on 2026-10-23.

Why it matters

  • Someone can re-run the script years later, without SUSHI.
  • A reader can see which reference and which parameters were used.
  • Built from the metadata: species, groups and the reference come from the DataSet table. The script calls STAR, featureCounts and the other tools.
  • Paper on SUSHI, the predecessor: Hatakeyama et al., “SUSHI: an exquisite recipe for fully documented, reproducible and reusable NGS data analysis”, BMC Bioinformatics 17:228 (2016). doi:10.1186/s12859-016-1104-8

What it does not show

  • The raw reads: the folder points to them, it does not copy them.
  • The job log: it is shown on the Jobs page.

Which Apps you are offered

Job states and the form

  • The form is filled in for you; the values are suggestions. For STAR, check the genome and whether the reads are paired-end.

  • running, success: the new DataSet appears when it is done.
  • fail: open the job’s log. Its last lines usually say what went wrong.

  • Every parameter: each App has its own. The form shows a short help text next to many of them.

API and tokens: how a program uses Omics-Studio

Details · slide 11 (2 of 2) · API

An API: a door for programs

  • A program sends a request to an address and gets data back, without a web page.
  • On the real system a program signs in without a password: it shows a short code, you approve it in B-Fabric, and the program receives a token that works for a limited time.
  • The right to submit jobs is a separate scope on the token. Without it, the API answers 403 insufficient_scope.
  • So an AI agent such as Claude Code can read datasets and submit jobs without ever holding a password.

What a request looks like

curl -H "Authorization: Bearer $TOKEN" \
     <OMICS_STUDIO_API>/api/v1/projects

curl -X POST -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"job": {"dataset_id": 12345,
          "app_name": "Fastqc",
          "parameters": {"cores": 1}}}' \
     <OMICS_STUDIO_API>/api/v1/jobs

The first lists your projects; the second submits FastQC on a dataset. OMAKASE submits its jobs through this same door.

Appendix A2 (2 of 2)

The order of the checks

  • 1. The dataset’s Species column names one species on FGCZ’s curated list → its reference is used.
  • 2. Otherwise, the species on the order’s B-Fabric samples.
  • 3. Otherwise, the LLM is asked to pick one name from the list, or UNKNOWN.
  • Code then checks: the name is on the list, the reply came from the expected model on an FGCZ server.
  • A person must confirm the suggestion before the chain may start.
  • What the model is shown: the species fields, the sequencing application, probe-set names. Never sample names or customers’ free text.

What it does not show

  • How often step 3 is needed: about half of FGCZ’s raw datasets name a curated species in step 1.
  • Whether the model’s suggestions are good: step 3 was added in October 2026 and is a prototype.
  • Datasets with two species: there is no single reference, so OMAKASE refuses.

Why a closed list? A free answer could be a genome build that does not exist (a hallucination). A name on a list can be checked by code.

Past orders do not agree on one right analysis

Appendix A3 (2 of 2)

What “~1 in 5” means

  • For each kind of order (service type), take the chain of apps used most often in the past.
  • Ask: would proposing that chain have been right for each order? About one time in five, yes.
  • For standard sequencing orders it was right less than one time in ten: they used more than 100 different chains.
  • This simple rule is the bar any automatic choice has to beat.

What it does not show

  • That a trained model would do as badly: no model has been trained or tested on this yet.
  • That the data are bad: real analyses simply differ.
  • A test with fixed rules, written before any results, will decide later whether an automatic choice is good enough.

Appendix A4 (2 of 2)

The run on the previous page

  • FastQC, FastQ Screen, STAR, then featureCounts, on 2 mouse samples, on FGCZ’s test system (September 2026).
  • Side by side: 6 min 31 s from start to finish.
  • The same jobs one after another would have taken 12 min 13 s.
  • The recipe says which step waits for which (appendix A6).
  • featureCounts needs STAR’s output; starting it anyway would only fail again. So OMAKASE stops the chain and records which step failed and why.

What it does not show

  • Real datasets: with more samples, STAR takes much longer and the saving changes.
  • Every failure stops the chain: a short cluster hiccup is retried once before the chain stops.
  • Undoing work: jobs already running when another step fails keep running.

What a recipe file looks like

Appendix A6

A recipe, shortened

id: rnaseq_meeting_shape
version: 2
steps:
  - id: fastqc
    app: FastqcApp
    after: []            # starts with the chain
  - id: fastqscreen
    app: FastqScreenApp
    after: []
  - id: star
    app: STARApp
    after: []
    params:
      refBuild: "{{ reference_for(species) }}"   # looked up (appendix A2)
  - id: featurecounts
    app: FeatureCountsApp
    after: [star]        # waits for STAR only
match:
  service_type: []        # empty: never chosen automatically

How to read it

  • A recipe is a text file (YAML). A bioinformatician writes it and signs it off; an AI may only draft one.
  • after says which step waits for which. Empty means “start with the chain”.
  • The genome is not written in: it is filled in from the dataset’s Species before a person approves.
  • There is no differential-expression step: choosing the comparison groups is a judgement nothing here can make.
  • A recipe has a version. A proposal records which version it used, so a result can be traced back.
